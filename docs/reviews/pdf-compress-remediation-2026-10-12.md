# PDF 압축 모듈 리뷰 수정 검증

2026-10-12. 범위는 `modules/pdf-compress`의 기존 리뷰 지적 3건이며, 버전은 0.1.4다. GPT 6.1 Sol 작업자 3명이 항목별 구현을 맡았고, 다른 항목 교차 리뷰와 부모 에이전트의 실제 브라우저 통합 검증을 거쳤다.

## 수정

| 항목                   | 재현 조건                                                                                                   | 수정                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 본문 손상              | 간접 참조 `/Length`를 쓰는 PDF 내용 스트림에 `endstream` 문자열이 있으면 pdf-lib가 내용을 짧게 읽을 수 있음 | 직렬화 전에 모든 원본 스트림의 선언 길이와 파싱된 길이를 비교. 불일치·미확인 시 원본 바이트 반환    |
| 설정 복원 경합         | 저장된 품질 30이 늦게 도착해 사용자가 방금 고른 품질 100을 덮어씀                                           | 사용자의 변경을 우선하고, 설정 준비 후 최신 값을 실행 단위로 고정. 대기 중 취소·언마운트 처리       |
| 사전 검사 중 화면 정지 | 작은 압축 파일에 큰 PDF 객체가 들어 있어 메인 스레드의 이미지 크기 사전 검사가 오래 걸림                    | 사전 검사를 별도 Worker로 이동. 원본 사본만 전송하고 취소·90초 제한·오류 시 Worker와 관련 자원 정리 |

새 의존성·캡·보안 설정·라이선스 변경은 없다. 기본 모드는 문서 구조 유지이며, 위험하거나 효과 없는 재작성은 원본 복사로 처리한다. 모든 입력 파일은 기존과 같이 보존한다.

## 확인된 결과

- PDF 모듈의 테스트 9개 파일, 59개 테스트 통과. 내용 스트림·JPEG·서명·배치·설정 복원·사전 검사 Worker를 포함한다.
- 본문 손상 재현 PDF: 5,695바이트 그대로 반환. 독립 PDF.js 추출에서 `BEFORE endstream AFTER`와 `TAIL TEXT MUST SURVIVE` 모두 유지.
- 합성 일반 RGB JPEG 4쪽: 3,049,878 → 640,682바이트. PDF.js로 검색 텍스트, 회전별 페이지 크기, 링크와 양식 주석, 제목 및 첨부 파일의 실제 20바이트 내용을 전후 비교했다. 양식 값도 재확인했다. 압축 전후 페이지를 렌더링하여 본문과 배치를 확인했다.
- 별도 이미지 PDF 변환: 1쪽 300×400pt 출력과 텍스트가 이미지로 변환된 결과 확인.
- 24MiB 문자열 객체를 포함한 25,138바이트 PDF: 사전 검사 2,967ms 동안 10ms 간격 heartbeat 198회, 최대 간격 17ms. 50ms 후 취소를 예약했을 때 54ms에 `CANCELLED` 반환, 입력 바이트 재사용 가능. 시간은 해당 실행 환경의 측정 예시다.
- 실제 모듈 화면: 두 파일을 자동 처리하여 하나는 압축, 하나는 원본 복사. 저장 경계에서도 원본 바이트 동일성을 확인했다.
- 실제 설정 화면: 사용자가 고른 품질 100 뒤에 저장된 품질 30이 도착해도 화면과 실행 시 저장 설정 모두 100 유지.
- `pnpm pack:module pdf-compress` 통과. 패키지에 새 사전 검사 Worker와 기존 압축·출력·PDF.js Worker 및 로컬 PDF 자산 포함.

브라우저 검증에는 실제 모듈 UI, 실제 압축·검사 Worker와 PDF.js를 사용했다. OS 파일 선택·읽기·저장 및 storage 응답은 SDK mock host로 대체했다. Windows 설치본 전체의 검증이나 배포 결과는 아니다.

패키지: `target/deckmod/pdf-compress-0.1.4.deckmod`, 3,155,067바이트. SHA-256: `ee54c40b7d3c86bd0d47eaf658cb62c67968ed4e062600ebd8ae031a790dc138`.

## 앞선 전체 저장소 검증

PDF 수정 직후의 `pnpm verify`는 전체 통과하지 못했다. Rust 실행 경로를 보완한 실행에서 lint와 typecheck는 통과했고, 다음 PDF 외 실패가 관찰됐다.

- `check-gen`: `apps/desktop/src/generated/third-party.json`과 현재 설치 그래프의 차이. 생성기를 메모리에서 재실행한 결과 기존 427개에 npm `@types/react@19.3.0` MIT 고지 1개가 추가되는 차이만 있었다. 이 고지는 기존 셸의 Fluent 의존 경로에서 발생하며 PDF 모듈의 버전 변경이나 새 의존성으로 생긴 차이가 아니다. 생성물은 수정하지 않았다.
- `SchoolData.test.tsx`: 15개 중 5개 실패.
- `meeting-note/src/App.test.tsx`: 22개 중 1개 실패.
- `duty-planner/src/App.test.tsx`: 25개 중 4개 실패.
- `MessagingConfirmation.test.tsx`: 4개 중 1개 실패.

검증 도중에도 다른 작업의 셸·공통 UI·새 모듈·규격 변경이 같은 작업 폴더에 계속 반영됐다. 이 실행은 테스트 단계에서 중단했으므로 당시 네이티브 검사와 나머지 검사기는 완료하지 못했다. 이 단계에서는 PDF 변경을 커밋·배포하지 않았다.

이후 사용자가 PDF 외 실패 해결을 요청했다. 생성물 동기화와 UI 테스트 후속 조치 및 최종 전체 검증 결과는 [후속 수정 기록](pdf-external-verify-remediation-2026-10-12.md)에 정리한다.

전체 실행 로그는 `target/pdf-fix-qa/verify.log`, 패키징 로그는 `target/pdf-fix-qa/pack.log`에 있다. 화면 확인 자료는 `output/playwright/pdf-fix-batch.png`, `pdf-fix-settings.png`, `pdf-fix-visual.png`다. 이 문서의 패키지·로그·화면 확인 경로는 원 작업 폴더 `D:\codex_work\teacherdeck` 기준이다. 이 경로들은 로컬 검증 산출물이며 Git에 포함하지 않는다.
