# 파일명 문서 분석·PDF 개인정보 탐지 보완

작성일: 2026-10-11. 파일명 정리 0.1.2, PDF 개인정보 지우기 0.1.3의 구현 범위다. 전체 검증·릴리스 빌드·설치본 실기 결과는 통합 담당이 별도로 기록한다.

## 원작 규칙과 구현

원천은 `D:/codex_work/programs/rename/processor.py`의 `_extract_date_priority`, `_extract_month_detail`, `_extract_category`, `_extract_title_heuristic`과 같은 폴더 `config.py`다. 코드·설정만 읽었으며 사용자 문서나 작업 로그는 읽지 않았다.

- 시험·평가 월 우선과 편집 날짜 제외를 복구했다. 합성 `편집일 2026년 3월 1일 / 2026학년도 9월 고3 모의평가`의 월은 03에서 09로 바뀐다. 구분자 날짜도 같은 경계로 검사한다.
- 학년도는 유지한다. 학기·분기·반기로 월을 추정할 때 근거에 추정을 표시한다. 수능 교재 이름만으로 11월을 만들지 않는다.
- 시험명·발행기관 이름에서 수학/과학을 과목으로 잘못 얻지 않는다. 괄호 안 상세 과목과 I/II/1/2 단계를 사용하고, 사용자가 지정한 분류 키워드를 우선한다. 고정 교시로 과목을 추론하는 것은 수능 문서에만 한정한다.
- 문서 상단의 후보를 직접 고치는 기존 화면·수동 이름 유지·정확 Excel 연결·새 결과 복사·보호된 원본 변경/undo는 유지한다. 원작의 모든 휴리스틱과 전체 문서 분류 사전을 그대로 이식했다고 주장하지 않는다.

## 개인정보 탐지와 삭제 경계

좌표상 같은 행의 가까운 글자를 연결하며 넓은 열 간격을 넘지 않는다. 90도 단위 읽는 방향을 반영하되 실제 제거 좌표는 원본 글자 객체의 화면 경계를 사용한다. 분할된 라벨·한글 이름, 라벨이 있는 영문 이름, 라벨 아래의 가까운 값도 후보가 된다. 영어 이름은 일반적인 Latin 표기와 공백·하이픈·아포스트로피를 지원하며 임의 언어 전체를 이름으로 판정하지 않는다.

주소의 가까운 정렬된 다음 네 행까지 확인하며 주소 요소가 있는 행만 포함한다. 새 항목·다른 열·떨어진 문단·다른 글자 방향에서 멈춘다. 비정형 줄배치와 주소 표기는 여전히 누락될 수 있다. 라벨 없는 이름은 추측하지 않고 기존 명단·검색어를 사용한다. 화면에 포함 스위치와 입력 수·발견 영역 수를 함께 보여준다.

후보와 같은 글자 객체의 주변 글자까지 제거될 수 있으므로 페이지별 확인이 필요하다. 선택한 원문 객체 전체의 경계를 덮은 픽셀을 치환하고 새 이미지 PDF를 만드는 출력 경로는 유지한다. 원문 객체를 새 PDF에 복사하지 않고 텍스트·주석·첨부·속성을 다시 검사한다. 자동 탐지의 완전성이나 OCR 검수를 수행했다고 표시하지 않는다.

회귀에는 편집일/시험월 충돌, 상세 과목과 시험명 오탐, 라벨·이름의 분할/열 분리, Latin 이름, 라벨과 같은 이름 값, 여러 줄 주소와 다음 항목 경계, 검색어 포함 UX를 넣었다. 실제 PDF.js로 4방향 회전의 Latin 이름을 읽고 모든 관련 글자 객체가 후보 영역 안에 들어가는지 검사한다. UserUnit/CropBox 8개 기존 사례와 새 PDF 객체 재열기 검사도 유지한다. 브라우저 픽셀 결과와 Windows 파일 선택·저장은 별도 실기 범위다.

두 모듈 지정 회귀는 9개 파일·54개 테스트가 모두 통과했다(`target/adversarial-review/file-mask-followup-tests.log`). 두 모듈 전체 src ESLint와 범위 diff 공백 검사도 통과했다. 지정 TypeScript 확인은 병렬 구현 중인 확장 화면의 SDK 생성 타입·이벤트 미생성 오류로 완료되지 않았으며 전체 타입 검사·verify는 통합 담당의 생성 후 검증을 따른다. 첫 병렬 PDF 테스트에서는 공용 임시 SSR 캐시 파일 누락이 발생했고, 이 작업 전용 target 임시 디렉터리로 분리한 최종 지정 실행에서 모든 원래 단언을 유지해 통과했다.

## 로컬 OCR 후속 설계 — 현재 제품에 추가하지 않음

필요 기능은 글자 레이어가 없는 스캔 PDF의 선택 페이지를 PC 안에서 읽어 **검수할 후보와 위치**를 제공하는 것이다. 사람 이름의 무라벨 자동 추정이나 100% 개인정보 발견은 목표로 삼지 않는다. 먼저 명단·검색어/형식·라벨 탐지와 결합한다.

검토 후보는 `tesseract.js 6.0.1`과 `tesseract.js-core 6.0.0`, `tessdata_fast 4.1.0`의 `kor.traineddata`·`eng.traineddata`다. 엔진 패키지와 언어 데이터는 Apache-2.0 원천을 확인했다. 이는 검토 버전이며 실제 파일을 내려받아 크기·SHA-256을 확정하거나 설치하지 않았다. [JS 원천](https://github.com/naptha/tesseract.js/blob/v6.0.1/package.json), [core 원천](https://github.com/naptha/tesseract.js-core/blob/v6.0.0/package.json), [언어 데이터 라이선스](https://github.com/tesseract-ocr/tessdata_fast/blob/4.1.0/LICENSE)를 기준으로 정확한 lock과 전이 의존성 고지·동봉 바이트 해시 검토가 선행되어야 한다.

구현안은 모듈 안 단일 Worker, LSTM 모드·한/영 두 모델, 명시적 ‘이 페이지 이미지 글자 읽기’다. PDF.js의 현재 렌더 좌표에서 150 DPI로 한 쪽씩 처리하고 기존 2,400만 화소/100쪽 상한을 유지한다. 90초 작업 제한·취소 시 Worker 종료·이전 수동 영역/출력 보존을 적용한다. 작은 글자의 확대는 같은 화소 상한에서 사용자가 선택한다. 성능·한글 정확도 수치는 합성/저사양 실측 전에 약속하지 않는다.

모든 Worker·WASM·모델 URL은 모듈의 자체 동봉 경로다. `workerBlobURL:false`, `cacheMethod:'none'`, `gzip:false`를 명시해 외부 CDN·IndexedDB·웹 저장소를 사용하지 않는다. 로깅은 개수·진행률·오류 코드만 허용한다. 기존 CSP에서 동작하는지를 먼저 검증하고 eval·외부 연결 권한을 자동 추가하지 않는다. API는 기본 text 출력 외 `blocks:true`로 위치 정보를 요청한다. [공식 API](https://github.com/naptha/tesseract.js/blob/v6.0.1/docs/api.md)를 따른다.

OCR의 낮은 신뢰도·빈 인식·일부 실패를 ‘개인정보 없음’으로 처리하지 않고 페이지별 미검수 상태와 수동 영역 안내를 유지한다. OCR 단어/줄 좌표를 PageInfo로 환산해 기존 후보 선택·픽셀 치환 출력에 연결한다. 검증은 서로 다른 합성 한글/영문 이름·전화·주민번호·여러 줄 주소·회전·UserUnit/CropBox, 흐릿한 입력과 깨진 모델, 완전 오프라인/CSP, 취소·시간 초과·한도, 실제 출력 픽셀/잔여 글자 OCR을 포함한다. 입력 인식과 독립 출력 검증을 혼동하지 않는다.

새 엔진·모델과 전이 의존성, 동봉 자산/라이선스의 정확한 승인·원문 고지·해시·크기 검토는 통합 담당의 구체 제안에서 확정한다. 기존 PDF 탐지 보완에 이 의존성을 몰래 추가하지 않는다. 새 호스트 명령·캡·ACL은 이 모듈 내부 OCR 설계에 필요하지 않다.
