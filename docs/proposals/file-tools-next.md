# 다음 파일 도구 구현 제안

작성일: 2026-10-11. 상태: **2026-10-11 사용자 승인 완료: 파일명 통합안 전체·fs 1.3/file-ops 1.0·Windows FFI 경계·PDF 글꼴 예외. 파일명 도구 구현과 범위 검증을 진행했으며 최종 통합 검증은 루트 담당이 수행한다**. 원본 근거는 [흐름 대응표](../reviews/file-tools-original-workflows.md)에 있다. 이미 승인된 fs 1.2의 읽기·새 결과 저장 권한을 원본 변경 권한으로 확대 해석하지 않는다. 관련 기준은 [제품 계획 4·5·8절](../PRODUCT_PLAN.md), [캡 규격](../spec/capabilities.md), [작업 절차](../spec/process.md), [개인정보 원칙](../spec/privacy.md)이다.

## 제안: 파일명 정리 통합 화면과 안전한 실행

- 정지 조건: 원본 이름 변경/복구에 필요한 새 호스트 캡, 복사 결과를 지우는 undo, 캡 계약·라이선스 변경이 필요한 경우 GEN-005. 파일명 도구는 사용자가 구체 기획을 확인한 뒤 구현하기로 한 범위다.
- 배경: 일반 패턴·엑셀과 문서 분석을 따로 실행하면 같은 파일 목록·충돌 처리·undo 흐름을 반복한다.
- 제안: `file-rename` 하나에 이름 재료 방식만 **직접 패턴 / 엑셀 연결 / 문서 정보**로 선택한다. 공통 `ToolLayout`은 입력→옵션→미리보기→실행→결과를 유지한다. 방식 변경으로 이미 추가한 목록이나 수동 수정값을 잃지 않는다.

### 구체 화면 흐름

1. 파일을 추가한다. 목록에서 파일명·크기·수정일 정렬, 선택 행 위/아래 이동, 선택 제거·비우기를 제공한다. 폴더는 최상위만 기본, 하위 폴더는 켠 경우만 읽는다.
2. 원본·연번·날짜·직접 문자열·엑셀 열·문서 연도/월/분류/학년 블록을 조합한다. 텍스트 패턴 편집과 템플릿 저장을 모두 제공한다. 원본 확장자는 별도로 붙인다. 날짜는 작업 계획 생성 때 고정한다.
3. 엑셀을 넣으면 시트·헤더 행·필요 열을 고른다. 매칭 방식은 **학번 정확 일치 / 번호 정확 일치 / 기존 이름 정확 일치 / 현재 목록 순서**다. 파일 쪽 키는 이름 전체 또는 사용자가 지정한 구분 부분을 미리보기로 확인한다. 학번의 선행 0을 임의로 없애지 않고, 번호 숫자 정규화는 선택한 경우만 한다. 중복 키·빈 키·파일 여러 개와 같은 행이 연결되는 경우는 미연결로 남긴다. 복합 추측 매칭은 제공하지 않는다. 미연결만 엑셀 행을 직접 지정한다. 불일치 건수와 사용되지 않은 행을 표시한다.
4. 미리보기 행에는 원본, 연결 근거/엑셀 행, 이름 재료, 최종 이름, 상태를 표시한다. 문서 추출값은 수정할 수 있다. Windows 예약명·금지문자·끝 점/공백·길이·대소문자 충돌·서로 이름 바꾸기를 검증한다. 잘라내기·빈 변수 대체는 사용자 확인 없이 확정하지 않는다.
5. 기본 **새 폴더에 복사**로 실행한다. **원본 이름 변경**은 별도 선택과 실행 요약 확인 후 수행한다. 성공·실패·미처리와 실패만 재시도, 취소, 결과 폴더 열기를 제공한다.
6. 제한된 이력에서 되돌린다. 변경·이동·다른 파일로 대체된 결과는 자동 복구하지 않는다. 이력은 일반 로그와 분리된 호스트 전용 로컬 데이터이며 모듈에는 불투명 이력 핸들과 건수만 노출한다.

### 호스트 계약 초안

기존 fs 1.2 조합으로 결과 복사는 가능하다. 폴더 열거는 **fs 1.3 minor** 후보 `listFiles({folderHandle,recursive,cursor?,limit}) → {files: FileHandleInfo[],nextCursor?}`로 추가한다. 루트는 사용자 선택 폴더, reparse 거부, 파일만, 결과 최대 2,000개·페이지당 최대 128개, 제한 초과를 명시한다. 상대/절대 경로는 모듈로 반환하지 않는다.

원본 변경은 읽기 권한과 분리된 **新 `file-ops` 1.0** 캡 후보다. 아래 승인된 계약은 Rust 원천과 SDK에 연결되었으며 세부 반환값·한도는 [파일 작업 규격](../spec/file-operations.md)과 [ADR-0019](../adr/0019-protected-file-operations.md)에 확정했다.

| 메서드 초안     | 인자·결과 초안                                                                                           | 보호 조건                                                                                                                       |
| --------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `planRename`    | `{items:[{sourceHandle,targetName}]}` → `{planHandle,items:[{sourceHandle,finalName,status}],expiresAt}` | 단일 이름만, 원본 부모 밖 이동 금지, 원본·목적지 동일성 확인, 한도 2,000개                                                      |
| `executeRename` | `{planHandle}` → `{historyHandle,success,failed,notStarted}`                                             | 실행 전 host 확인창으로 명시 선택. create-new·덮어쓰기 없음. 이름 교환/대소문자 변경은 같은 폴더의 host 소유 임시명 단계로 처리 |
| `listHistory`   | `{cursor?}` → 제한된 건수·상태·불투명 이력 id                                                            | 경로·파일명·내용 노출 없음. 앱 재시작 후에도 host가 실체 재확인                                                                 |
| `undoRename`    | `{historyHandle}` → `{success,failed,blocked}`                                                           | 파일 동일성·내용 변경·기존 이름 점유 검사, 수정된 파일 보존, 되돌릴 수 없는 항목 설명                                           |

취소 API와 복사 undo는 별도 설계다. rename 실행은 이름 교환을 포함한 연결군 단위로 순차 수행하고 UI 취소는 다음 군 시작을 막는다. 실행 중 호출의 호스트 취소를 주장하지 않는다. 복사 undo의 완성 결과 삭제는 승인 전 구현하지 않는다. 원본 이름 변경 계획은 실행 직전에 host가 다시 검사하며 표시 후 생긴 충돌은 새 이름으로 몰래 바꾸지 않고 해당 항목을 중단한다.

- 검토한 대안: fs만으로 새 복사본을 만들면 원본 변경·지속 undo를 제공할 수 없다. JS/WASM은 OS 파일 이름 변경 권한이 없다. 읽기 핸들의 쓰기 승격은 권한 분리를 깨므로 채택하지 않는다.
- 영향: 모듈 신규 0.1.0, fs minor·새 캡·SDK/app minor 및 ADR/spec/Rust 원천→gen→테스트→버전/CHANGELOG 순서를 적용한다. 매니페스트·브리지 envelope·보안 설정은 그대로 유지하는 안이다. 실제 ACL 추가가 필요하면 구체 변경을 별도 검토한다.
- 필요한 승인: 통합 화면 3가지 방식, 정확 매칭/미연결 수동 처리, 새 폴더 복사 기본/원본 변경 선택, fs 폴더 열거와 file-ops 계약, 지속 undo 범위. API 세부안 중 미정인 파일 동일성 식별·트랜잭션 회복·이력 보호 방식은 구현 전 최종 ADR로 확정한다.

## 제안: PDF 엔진과 실제 개인정보 제거

- 정지 조건: 새 라이브러리의 라이선스 allowlist 변경, `packages/*`에 공통 PDF 런타임을 둘 경우 GEN-004, 구조 redaction을 위해 새 호스트 캡/helper를 도입하는 경우 GEN-005. 모듈만의 허용 라이선스 JS 의존성은 GEN-004 대상이 아니지만 이번 엔진 선택을 먼저 확인한다.
- 배경: 현재 레포에는 PDF 엔진이 없다. 원본 PyMuPDF의 실제 redaction 성질과 로컬 처리를 유지하면서 자동 탐지를 추가해야 한다.
- 제안: 모듈 내부에 PDF 처리 어댑터를 두고 **PDF.js의 로컬 텍스트·좌표·렌더**, 새 PDF 작성은 **pdf-lib**를 후보로 삼는다. pdfjs-dist 6.4.299(설치 파일 34,913,648바이트), pdf-lib 1.17.1(19,461,112바이트)을 확인했다. 전이 의존성·WASM/cmap/font 자산은 별도로 검사한다. CDN·외부 OCR·외부 폰트 요청을 하지 않으며 Worker·필요 자산을 모듈에 동봉한다. 다른 모듈의 내부 코드를 import하지 않는다.

두 엔진은 PDF 파싱/렌더와 새 PDF 작성에 적합하지만, `drawRectangle`로 원문 위에 색만 칠하는 방식은 제거로 인정하지 않는다. [PDF.js 공식 설명](https://mozilla.github.io/pdf.js/)과 [pdf-lib 공식 API](https://pdf-lib.js.org/)를 참고했다. PDF.js는 [Apache-2.0](https://github.com/mozilla/pdf.js/blob/master/LICENSE), pdf-lib는 [MIT](https://github.com/Hopding/pdf-lib/blob/master/LICENSE.md)로 현재 허용 목록에 있다. 패키지 전이 의존성은 별도로 검증한다.

### 현재 제거 방식과 후속 대안

| 방식              | 제거 구현                                                                                                                                 | 원본 UX·내용 영향                                                                                               | 승인 범위                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| A. 새 이미지 PDF  | 모든 페이지를 로컬 렌더 → 선택 영역의 **픽셀을 실제 치환** → 완전히 새 문서에 바뀐 이미지만 삽입. 원본 페이지·텍스트·객체를 복사하지 않음 | 지정 영역 내용과 숨은 원문/첨부/속성을 넘기지 않음. 대신 검색/복사·벡터·양식·접근성 구조가 없어지고 해상도 영향 | 기존 사용자 요구에 따라 구현. 원본 보존·출력 품질 안내와 제거 검사 적용                             |
| B. 구조 redaction | 원본과 같은 redaction 엔진으로 선택 텍스트/픽셀/벡터를 제거하고 새 전체 저장·객체 정리·속성/주석/첨부 제거                                | 영역 밖의 검색 가능한 텍스트·벡터를 최대한 유지                                                                 | MuPDF/PyMuPDF 계열 엔진, 배포 크기·실행 경계·라이선스 승인 검토. 새 캡/helper면 별도 구체 계약 필요 |

현재 구현은 **A. 새 이미지 PDF**를 사용한다. 이는 사용자의 실제 내부 정보 제거 요구에 부합하며, 출력 전에 이미지 문서로 바뀌고 텍스트 검색·벡터·양식 등이 없어지는 것을 분명하게 안내한다. B는 검색 가능한 원문 구조를 보존하는 후속 대안이며 이번 모듈 구현 범위가 아니다. MuPDF는 [공식 라이선스 문서](https://mupdf.readthedocs.io/en/latest/license.html)에 따른 별도 검토가 필요하며 현재 allowlist에 AGPL은 없다. 이 조사만으로 라이선스 예외를 추가하거나 native helper를 실행하지 않는다.

### 자동 탐지와 수동 입력 흐름

PDF 추가→자동 후보 분석→분류별 건수와 페이지 미리보기→검색어/명단/TXT·CSV 목록 추가→필요한 영역 직접 지정→제거 결과 새 PDF→재검증·저장 순서다. 후보는 기본 선택하되 해제·추가가 가능하고, 발견하지 못한 페이지/유형을 성공으로 표시하지 않는다.

- 전화번호: 한국 전화 형식·구분자/공백 변형을 검사한다.
- 주민번호: 6+7 자리 형태와 날짜·허용 접두 조합 등을 검사한다. 잘못된 형태도 주민번호 문맥이면 별도 후보로 남긴다.
- 계좌번호·생년월일·학번: 숫자만으로 확정하지 않고 관련 표 헤더/라벨과 선택한 열·명단 규칙을 결합한다. 강한 패턴과 문맥 후보를 구분한다.
- 이름·주소: 명단·검색어와 `이름/성명/주소` 라벨 주변을 사용한다. 임의 한글 단어 전부를 이름으로 간주하지 않는다. 부분 주소·여러 줄은 전체 행/셀 영역을 후보로 묶고 근거를 표시한다.
- 스캔 페이지: 텍스트가 없다는 사실을 표시한다. 수동 영역은 가능하지만 자동 탐지를 완료했다고 말하지 않는다. 로컬 OCR 도입은 모델·성능·라이선스·자산 용량 제안 뒤 확정한다.

검증은 선택한 제거 영역의 렌더 픽셀, 출력 텍스트 재추출/검색, 이미지 XObject·내용 스트림·첨부·속성·주석·양식/숨은 텍스트의 잔존 여부를 교차한다. 합성 PDF에는 회전 0/90/180/270, 텍스트가 나뉜 번호·이름과 이미지·텍스트 겹침을 포함한다. CropBox 밖 내용과 이전 증분 저장 사례는 별도 확장 검증 항목이다. OCR 확인이 필요한 출력을 OCR 검사 없이 “개인정보 전체 제거”로 완료 처리하지 않는다. 일반 로그는 개수·오류 코드·진행률만 남긴다.

- 검토한 대안: 검정 도형 overlay는 제외. pdf-lib 원본 페이지 복사는 숨은 객체 잔존을 입증할 수 없으므로 A에 사용하지 않는다. 외부 OCR·서버 PDF 변환은 제품 약속과 충돌한다.
- 영향: `pdf-mask` 신규 모듈, `photo-extract` PDF 지원 버전 bump, `pdf-compress` 신규 모듈. 현재 A 모듈은 새 캡·CSP·ACL 변경이 없다. 최종 배포는 동봉 자산 라이선스와 실제 검증을 완료한 뒤 진행한다.
- 필요한 승인: PDF.js 동봉 폰트 중 LiberationSans의 GPLv2 + font exception 자산 예외는 부모 에이전트의 별도 라이선스 제안에서 검토한다. 현재 모듈 전용 Apache-2.0/MIT JS 의존성은 GEN-004 대상이 아니다. B 구조 엔진이나 로컬 OCR을 도입할 때는 실제 패키지·라이선스·호스트 계약을 별도 확정한다.

## PDF 사진 꺼내기와 압축의 구현 순서

1. PDF.js를 선택하면 `photo-extract`에 PDF 입력을 추가한다. 명렬표를 200 DPI로 렌더하고 사진 상자·페이지 텍스트 위치를 연결한다. 회전 좌표 보정, 상하좌우 px 안쪽 여백, 파일명 `{학년}_{반}_{번호}_{이름}`, 미확인 사진 보존을 원본 NEIS와 대조한다. 사진 영역 미검출·여러 후보·텍스트 없음은 미확인으로 남기고 수동 영역/이름 수정으로 해결한다. XLSX 원본 바이트 흐름은 유지한다.
2. 독립 PDF 압축은 **문서 구조 유지 압축**을 기본으로 하고 **페이지 이미지 재압축**을 보조 방식으로 구분한다. 문서 구조 유지 방식은 지원하는 RGB JPEG XObject와 객체 스트림을 최적화하고 텍스트·링크·양식·첨부를 유지한다. 서명 문서는 원본 바이트를 보존하며 특수 이미지 형식은 건드리지 않는다. 이 방식은 통합 담당이 별도로 구현·검수한다. DPI/JPEG 품질과 예상 결과를 보여주고 생성 후 페이지 수·크기·회전·렌더 품질·바이트 감소를 검사한다. 더 커진 결과를 압축 성공으로 표시하지 않는다. 텍스트/벡터 유지 최적화는 선택한 구조 PDF 엔진으로 별도 검증한다.
3. 파일명 도구는 승인된 기획/캡 계약부터, PDF 도구는 엔진 결정부터 시작한다. 각 도구의 실파일 흐름·키보드·DPI/테마·수백 파일 오류/취소를 확인하고 `pnpm verify`를 수행한다. 제안 문서 작성은 도구 구현 완료가 아니다.

## 이번 PDF 구현의 검증 상태

- pdf-mask: 실제 브라우저의 4쪽 합성 PDF(0/90/180/270도 회전, 80pt 하강부 문자 포함)에서 선택한 16영역의 내부 153,086픽셀이 모두 제거색이며 미제거 픽셀은 0이었다. 출력의 텍스트·첨부·제목이 없고 페이지 크기가 유지됐다.
- 원본 이미지 XObject 치수를 디코드 전에 검사한다. 2,500만 픽셀 입력이 SOURCE_IMAGE_TOO_LARGE로 차단되는 실제 사례와 단위 테스트를 확인했다.
- pdf-compress: 보조 이미지 PDF 방식의 실제 4쪽 합성 입력 6,813,417바이트가 1,116,254바이트로 줄어드는 것을 확인했다. 기본 문서 구조 유지·추가 즉시 처리 방식은 통합 담당이 구현·검수하며 이 이미지 방식의 결과를 구조 보존 증거로 사용하지 않는다.
- 모듈 내부 복제 build plugin을 사용한다. 다른 모듈·공용 빌드 helper를 상대 import하지 않는다. 모듈 단독 빌드·테스트는 진행하며 전체 verify와 배포 판정은 통합 단계에서 한다.
- 파일명 통합안과 호스트 캡 계약은 사용자 승인 후 구현했다. PDF 동봉 글꼴 예외도 승인됐으며 모듈별 자산 원문·출처·해시 생성과 검사에 연결했다. 최종 배포 판정은 통합 검증 뒤 루트 담당이 수행한다.
