# ADR-0014: 제한된 파일 읽기와 순차 결과 저장

- 상태: 승인됨
- 날짜: 2026-10-10
- 결정자: 프로젝트 소유자, “두 보완안 승인” 답변

## 맥락

[ADR-0012](0012-file-input-foundation.md)의 POST 수신 전 한도를 Wry 공개 API로 지킬 수 없었다. [후속 제안](../proposals/file-transfer-followup.md)의 전송 변경과 모듈 origin 분리를 사용자가 승인했다. 격리는 [ADR-0013](0013-module-origin-isolation.md)을 따른다.

## 결정

fs 1.1에 openRead/closeRead, createOutputFolder/beginWrite/writeChunk/commitWrite/abortWrite/closeOutputFolder를 추가한다. 선택한 파일·폴더와 결과 작업·읽기·쓰기 권한은 구분한다. 리소스 GET은 모듈별 origin과 128비트 난수 토큰을 검증하고 최대 256KiB를 반환한다.

쓰기만 기존 인증 브리지로 최대 64KiB u8 배열을 직렬 전송한다(CAP-003의 좁은 예외). POST 업로드는 제공하지 않는다. 청크 offset과 직전 동일 재전송을 검사한다. 실제 취소는 abortWrite이며, 게시가 먼저 완료된 파일은 보존한다.

원본과 기존 결과를 덮어쓰거나 삭제하지 않는다. 사용자 선택 폴더 아래 새 결과 폴더를 배타적으로 만든다. 임시 바이트는 TempArea에 두고, 새 결과 폴더의 호스트 소유 게시 준비물로 제한된 복사를 한 뒤 hard link로 최종 이름을 원자적으로 게시한다. Windows에서는 게시 준비물의 원래 파일 핸들을 읽기 공유만 허용한 채 유지하여 외부 수정·삭제를 막는다. 부모 디렉터리는 읽기·쓰기 공유를 허용하되 삭제 공유를 거부하여 게시와 폴더 보호를 함께 지원한다. 이 준비물에만 PRV-005의 위치 예외를 둔다. hard link 미지원 파일시스템은 오류로 중단하며 덮어쓰기 fallback은 없다. 완료 결과·사용자 추가 파일은 정리하지 않는다. 이 계약은 파일 게시 중간 상태를 노출하지 않기 위한 것이며 전원 장애까지의 영속성을 보장하지 않는다.

임시 작업은 전용 복구 기록에 생성 메타데이터와 제한된 블록 해시를 남긴다. 디스크 기록은 4MiB마다, 전체 수신 완료 및 게시 준비물 생성 시 수행한다. 다음 시작에서 소유권과 내용이 확인된 미완성 파일만 정리하고, 마지막 기록 이후 바뀐 파일·손상 기록·사용자 수정·추가 파일은 보존한다. 일반 임시 폴더의 재귀 삭제를 결과 파일 작업에 사용하지 않는다.

파일당 512MiB, 읽기 모듈당 4개, 쓰기 모듈당 1개·앱 전체 2개, 결과 작업당 파일 2,000개·합계 2GiB로 제한한다. 자원은 5분 미사용 만료와 모듈 언로드에 폐기하지만 완료 결과는 유지한다. 토큰은 앱 세션에만 존재하고 로그에 남기지 않는다.

## 결과

정상 SDK 전송의 메모리를 청크 단위로 제한한다. 악성 모듈의 모든 브리지/HTTP 요청을 파싱 전에 제한하는 전역 메모리 방어까지 보장하지 않는다. API·권한·청크·취소·원본 보존·다른 볼륨·Windows 모듈 로딩을 검증한다. 새 런타임 의존성과 Tauri ACL 확대는 없다. 앱은 0.1.0, SDK는 0.2.0으로 올린다.

## 대안

Wry 포크나 Win32 IStream 가로채기는 이번 범위에서 제외한다. 전체 바이너리의 브리지 전송, 기존 파일의 이동, 부분 파일을 완료 결과로 게시하는 방식도 사용하지 않는다.
