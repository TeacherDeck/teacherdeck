# 기존 도구를 TeacherDeck 모듈로 옮기기

이 문서는 기존 프로그램을 이 저장소의 모듈 구조에 맞춰 옮기는 실무 안내서예요. 규범 원천은 [docs/spec](spec/README.md)이고, 작업 지침은 [루트 AGENTS.md](../AGENTS.md)와 [modules/AGENTS.md](../modules/AGENTS.md)를 따라요. 이 문서에서 새 규격이나 권한을 정의하지 않아요.

기존 프로그램의 소스와 제품 요구사항을 확인했어요. 재사용할 기능과 모듈 구성은 [제품 개발 계획 초안](PRODUCT_PLAN.md)에 정리해요. 이 안내서는 2026-10-10에 반영한 공통 UI 규칙을 기준으로 하며, 실제 모듈 구현과 필요한 캡 확장은 각 설계안을 검토한 뒤 진행해요.

## 1. 먼저 알아둘 구조

기존 프로그램의 기능을 도구 단위로 나누고, 각 도구를 `modules/<id>`의 웹 번들로 만들어요. Python 실행 파일, Electron 앱, 네이티브 플러그인을 그대로 넣는 구조가 아니에요. 계산 로직은 모듈 안의 JS/TS 또는 WASM으로 옮기고, OS 기능은 SDK를 통해 호스트가 제공하는 캡을 호출해요.

| 위치               | 이식할 때의 역할                       | 먼저 볼 파일                                                                                   |
| ------------------ | -------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `modules/<id>/src` | 도구별 계산, 상태, 화면, SDK 호출      | [모듈 구성](spec/modules.md#2-모듈-구성)                                                       |
| `packages/sdk`     | 모듈에서 호스트 기능을 부르는 공개 API | [SDK 공개 API](../packages/sdk/src/index.ts), [클라이언트 구현](../packages/sdk/src/client.ts) |
| `packages/ui`      | WinUI 공통 컨트롤·타입 램프·공개 토큰  | [공통 UI](spec/design-system.md), [공개 API](../packages/ui/src/index.ts)                      |
| `apps/desktop`     | 셸과 Rust 호스트                       | [셸 지침](../apps/desktop/AGENTS.md), [호스트 지침](../apps/desktop/src-tauri/AGENTS.md)       |

모듈은 셸과 다른 origin의 iframe에서 실행돼요. `@tauri-apps/*`, 셸 내부 코드, 다른 모듈, SDK/UI의 내부 경로를 직접 import하지 않아요. 기존 도구끼리 함수를 직접 가져오는 방식도 먼저 정리해야 해요(MOD-005, MOD-006). 연결 과정은 [브리지 규격](spec/bridge-protocol.md)을 따르고 직접 `postMessage` 프로토콜을 새로 만들지 않아요.

## 2. 현재 구현된 기능과 아직 없는 기능

아래는 현재 [v1 캡 레지스트리](spec/capabilities.md#2-v1-레지스트리), [SDK](../packages/sdk/src/client.ts), [Rust 라우팅](../apps/desktop/src-tauri/src/caps/mod.rs)을 함께 확인한 범위예요. 이후 캡이 확장되면 이식 시점에 다시 확인해요.

| 캡              | 현재 호출 가능한 기능                                 | 이식할 때 주의할 점                                                                                  |
| --------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `system` 1.0.0  | `info()`                                              | 앱 버전, OS 정보, 로캘을 제공해요. 임의 프로그램 실행 기능은 없어요.                                 |
| `storage` 1.0.0 | `get`, `set`, `delete`, `keys`                        | 도구 설정과 프리셋용 JSON 저장소예요. 값당 256KB, 모듈 합계 5MB 제한이 있어요.                       |
| `fs` 1.1.0      | 파일 선택·정보·탐색기, 제한된 읽기, 새 결과 폴더 저장 | SDK `readChunks`·`writeBlob`을 사용해요. 원본 이름 변경·덮어쓰기·삭제와 폴더 열거는 제공하지 않아요. |
| `window` 1.0.0  | `setAlwaysOnTop`, `setFullscreen`                     | 호스트 메인 창의 상태를 바꿔요. 도구를 숨기거나 닫으면 호스트가 원래 상태로 돌려요.                  |

`deck.fs.pickFiles()`는 핸들과 표시용 이름·확장자·크기·수정 시각을 돌려줘요. 선택한 파일은 `deck.fs.readChunks({handle})`로 최대 256KiB씩 읽어요. 경로는 반환하지 않아요. 사용 모듈은 `requires.fs: "^1.1.0"`을 선언해야 해요. 정확한 계약과 예제는 [fs 규격](spec/capabilities.md#22-fs)과 [SDK 안내](../packages/sdk/README.md)를 참고해요.

저장은 `pickFolder` → `createOutputFolder` → `writeBlob` → `closeOutputFolder` 순서예요. 선택 폴더 아래 새 결과 폴더를 만들고, 이름이 겹치면 연번을 붙여요. 원본은 유지돼요. 쓰기는 64KiB씩 순차 전송하며 파일당 512MiB, 결과 작업당 2,000개·2GiB 제한이 있어요. 파일 변환 계산이나 Office 연동 자체를 이 API가 대신하지는 않아요. 파일명 도구도 원본의 이름을 바꾸는 방식은 별도 설계·승인 대상이에요.

다음은 [예정 캡](spec/capabilities.md#5-예정-캡)에 기록된 설계 방향이며 현재 제공되는 API가 아니에요.

- `fs` 후속 확장: 기존 파일의 이동·이름 변경 등 1.1 밖의 요구는 별도로 검토해요.
- `pdf`, `image`: 우선 모듈 내부 JS/WASM으로 계산을 처리하고, 필요한 경우에만 범용 네이티브 기능을 제안해요.
- `ocr`, `office`: 로컬 OCR이나 Office/한글 연동 방향이에요. 지금 사용할 구현은 없어요.
- `roster`: 도구 사이의 명단 공유 방향이에요. 현재 storage의 모듈별 격리를 우회하는 근거가 아니에요.

브리지에 장시간 작업의 진행률·취소 메시지 형식은 있지만, v1에서는 job 패턴을 예약한 상태예요([브리지 3절](spec/bridge-protocol.md#3-요청응답과-장시간-작업)). SDK의 취소 옵션이 있다는 이유만으로 호스트 변환 작업 전체가 준비됐다고 판단하지 않아요. 원격 카탈로그 서명·배포도 [예정 기능](spec/catalog.md#원격-카탈로그-서명-예정)이므로 로컬 패키징 성공을 원격 배포 완료로 보지 않아요.

## 3. 도구마다 먼저 받을 자료

첫 이식 때 아래 자료로 범위를 확정해요. 학생이나 학교의 실제 파일 대신 [합성 데이터](../fixtures/synthetic/README.md)와 가상값을 사용해요(PRV-004).

| 자료                         | 확인할 내용                                                    |
| ---------------------------- | -------------------------------------------------------------- |
| 소스 폴더 또는 저장소·브랜치 | 실행 진입점, 수정할 범위, 기존 테스트, 현재 변경사항           |
| 이식할 도구와 우선순위       | 한 모듈에 담을 사용자 작업, 유지할 기능, 이번 범위 밖 기능     |
| 실행 방법과 의존성 목록      | Python/Node/네이티브 라이브러리, 외부 실행 파일, 설치 전제     |
| 입력·출력 합성 예제          | 지원 확장자, 한 번에 처리할 파일 수·크기, 기대 결과            |
| 기존 화면과 핵심 사용 흐름   | 입력 → 옵션 → 미리보기 → 실행 → 결과, 오류·취소 흐름           |
| 기존 저자·라이선스 정보      | 가져올 코드와 에셋의 출처, 표시를 유지할 저자, 의존성 라이선스 |

이 자료로 도구마다 다음 표를 채워요. 아직 정해지지 않은 항목은 구현된 것으로 가정하지 않아요.

| 기존 기능                | 순수 계산으로 분리할 부분 | 현재 캡·UI로 연결할 부분                         | 부족한 호스트 기능       | 검증 예제                  |
| ------------------------ | ------------------------- | ------------------------------------------------ | ------------------------ | -------------------------- |
| 예: 파일명 규칙 미리보기 | 문자열 변환·충돌 판정     | `fs`로 파일 정보 선택, `ToolLayout`으로 미리보기 | 실제 이름변경은 API 없음 | 가상 파일명과 충돌 사례    |
| 예: 시간 계산·프리셋     | 시간 상태 계산            | `storage`, `window`, `@deck/ui` 화면             | 요구사항에 따라 판단     | 경과 시간·프리셋 복원 사례 |

## 4. 실제 이식 순서

### 4.1 하나의 도구를 생성해요

[모듈 생성 절차](../modules/AGENTS.md#모듈-추가-절차)에 따라 루트에서 실행해요. 아래 값은 실제 도구 이름과 기여자로 바꿔요.

```powershell
pnpm new:module <id> --name "<도구 이름>" --category utility --author "<실제 기여자>"
pnpm install
```

생성기는 [modules/_template](../modules/_template/)을 이용해 필수 파일과 `deckTemplate` 마커를 채워요. 기존 프로젝트 폴더를 `modules`에 통째로 복사하지 않아요(MOD-001). id와 category는 [매니페스트 규격](spec/modules.md#1-매니페스트-modulejson)을 따르고, `module.json`의 설명·저자·필수/선택 캡을 실제 구현에 맞춰 채워요. 생성기의 저자 기본값은 Git 설정을 사용하므로 확인 없이 확정하지 않아요.

### 4.2 계산을 UI·파일·OS에서 분리해요

기존 함수가 경로를 받고 직접 파일을 읽거나 UI 위젯을 바꾼다면 입력 데이터와 옵션을 받아 결과를 반환하도록 분리해요. 순수 계산은 DOM, SDK, 파일시스템, 전역 저장소에 의존하지 않게 두고, 원래의 기대 결과를 합성 예제로 검증해요. 시간에 의존하는 계산은 [타이머 로직](../modules/timer/src/timer.ts)처럼 현재 시각을 인자로 받아 테스트할 수 있어요.

Python 코드의 계산 알고리즘은 TS나 적합한 로컬 WASM 구현으로 옮길 수 있는지 검토해요. OS/COM 연동이나 외부 실행 파일 호출은 단순한 소스 복사로 모듈 안에서 실행할 수 없어요. 브라우저에서 쓸 라이브러리도 외부 요청 없이 번들되는지, 라이선스와 패키지 크기를 만족하는지 확인해요. 50ms 이상 걸릴 수 있는 연산은 Worker/WASM으로 분리해요(MOD-014).

### 4.3 기존 호스트 호출을 SDK로 바꿔요

[타이머 진입점](../modules/timer/src/main.tsx)을 따라 `connect()` 완료 후 `DeckProvider` 안에 화면을 렌더해요. 연결 실패 화면도 유지해요. SDK가 `hello`/`init`, origin 검증, 요청 식별자, 오류를 처리하므로 모듈이 이를 재구현하지 않아요.

| 기존 방식                                              | 이식 방향                                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `localStorage`, IndexedDB, 쿠키, 웹 캐시의 영속 데이터 | 설정·프리셋을 `deck.storage`로 옮겨요. 구조 검증과 기본값 복원을 함께 구현해요.             |
| 직접 OS 파일 선택, 절대 경로 전달                      | `deck.fs.pickFiles()`/`pickFolder()`와 반환 핸들을 사용해요.                                |
| 파일 드롭 이벤트의 경로 사용                           | `DropZone`으로 안내하고 `deck.on("fs.dropped", ...)`의 `files`를 받아요.                    |
| 항상 위·전체화면 네이티브 호출                         | `deck.window`를 사용해요.                                                                   |
| 임의 파일 읽기·쓰기, COM, 명령 실행                    | 현재 가능한 캡으로 표현할 수 있는지 검토하고, 부족한 기능은 제안 단계로 분리해요.           |
| 서버 API, 클라우드 OCR, CDN 에셋                       | 로컬 처리·로컬 번들로 바꿀 수 있는지 판단해요. 모듈의 외부 네트워크 요청은 허용되지 않아요. |

호출하는 캡은 모두 `module.json`의 `requires` 또는 `optional`에 선언해요. 선택 캡은 `deck.has()` 확인과 `CapabilityGate` 안내를 함께 써요(MOD-006, MOD-007). `fs.dropped`는 `fs` 캡이 있는 활성 도구에만 전달되고, [DropZone](../packages/ui/src/components.tsx)은 드롭 시각화 컴포넌트예요. DOM 드롭만 연결해서 호스트 핸들을 받는 흐름을 대신하지 않아요.

핸들은 모듈과 앱 세션에 종속돼요. 다음 실행에서 다시 사용할 영구 경로처럼 storage에 저장하지 않아요. SDK 호출 인자·결과 타입은 공개 export를 사용하고 생성 파일을 수정하지 않아요(GEN-006). 브리지 메시지는 JSON이며 1MB 제한이 있어요. 파일 내용을 Base64로 만들어 브리지나 storage에 넣는 방식으로 아직 없는 파일 전송 API를 대신하지 않아요(CAP-003, BRG-007).

설정 저장의 실제 예는 [recent.ts](../modules/timer/src/recent.ts)를 봐요. 저장값이 손상되거나 이전 버전에서 만들어져도 걸러 내고 안전한 값(빈 목록)으로 시작하는 패턴이 있어요. 경로·파일명·사용자 입력·storage 값을 로그나 오류에 출력하지 않아요([개인정보 규칙](spec/privacy.md#4-규칙)).

### 4.4 화면을 공통 UI에 맞춰요

기존 도구의 핵심 작업 흐름을 보존하면서 화면 구성과 스타일은 [디자인 시스템](spec/design-system.md)에 맞춰요. 버튼·입력·대화상자·글자 컴포넌트와 `makeStyles`, `tokens`, `deckTokens`까지 모두 `@deck/ui` 공개 진입점에서 가져와요. 아이콘만 `@fluentui/react-icons`에서 가져와요. 모듈의 Fluent 직접 import는 MOD-010 린트가 차단해요. 기존 CSS의 색·간격·폰트를 그대로 옮기지 않아요.

파일 일괄 처리 도구는 `ToolLayout.Section`의 `input`, `options`, `preview`, `run`, `result` 단계로 구성해요. 빈 화면은 `EmptyState`, 파일 입력 안내는 `DropZone`, 설정 묶음은 `SettingsCard`/`SettingsExpander`를 먼저 검토해요. 공통 패턴이 없을 때는 [공통 UI 추가 절차](../packages/ui/AGENTS.md#컴포넌트-추가-절차)에 따라 제안하고 모듈마다 중복 구현하지 않아요(UI-006).

입력은 `TextBox`, `NumberBox`, `ComboBox`, `RadioButtons`, `ToggleSwitch` 등의 공개 컨트롤을 써요. 입력의 `header`는 접근성 이름이므로 반드시 제공하고, 설정 카드 안에서는 `showHeader={false}`로 중복 표시만 숨겨요. `onChange`는 컨트롤이 전달하는 값을 받아요. `SettingsCard`의 `action`과 카드 전체 클릭용 `onClick`은 함께 지정하지 않아요. 상태 안내는 `InfoBar`, 진행은 `ProgressBar`/`ProgressRing`, 확인은 `ContentDialog`를 써요. 정확한 props와 결과 형식은 [공개 API](../packages/ui/src/index.ts)와 [컨트롤 구현](../packages/ui/src/controls.tsx)을 확인해요.

글자는 지정된 시스템 폰트와 `Caption`부터 `Display`까지의 타입 램프를 사용해요. 기존 프로그램의 폰트 번들을 가져오거나 외부 폰트·에셋을 실행 중 내려받지 않아요. 한국어 문구는 짧은 해요체와 동작어 버튼을 사용하고, 오류는 원인과 다음 행동을 설명해요(UI-007). 키보드만으로 모든 기능을 조작할 수 있는지, 포커스가 보이는지, 라이트/다크와 실제 텍스트 150%·DPI 200%에서 잘리지 않는지 확인해요(UI-005). 갤러리의 글자 크기 토글만으로 Windows 배율 검증을 대신하지 않아요.

### 4.5 테스트하고 앱에서 확인해요

순수 계산은 vitest로 입력·결과·경계값을 검증해요. SDK 연동은 `@deck/sdk/testing`의 `createMockHost`로 필요한 캡만 허용하고 실제 메서드 핸들러를 제공해요. [최근 기록 테스트](../modules/timer/src/recent.test.ts)는 `connect({ window: host.window })`, `host.requests` 확인, `deck.dispose()`의 예를 보여 줘요.

도구 요구사항에 맞춰 정상 처리, 빈 입력, 잘못된 설정, 선택 취소, optional 캡 없음, 실패 후 재시도를 확인해요. mock이 미구현 API를 성공시킨다고 실제 호스트 기능이 생기는 것은 아니므로, 현재 레지스트리에 있는 호출만 연결해요.

```powershell
pnpm exec vitest run modules/<id>/src
pnpm verify
pnpm tauri dev
```

`pnpm verify`는 [CI와 같은 전체 검사](spec/ci.md#1-pnpm-verify)예요. `verify:fast`만 통과한 상태로 완료를 선언하지 않아요(GEN-003). 규칙 오류는 해당 spec을 확인해 코드에서 고치고 검사기·스펙을 완화하지 않아요(GEN-001). 실제 앱에서는 모듈 열기, 화면 전환, 설정 복원, 오프라인 동작, 관련 파일 대화상자와 창 상태 복원을 확인해요. 학교 PC와 비슷한 작은 화면·낮은 사양에서도 주요 작업을 확인해요.

### 4.6 패키징하고 변경사항을 정리해요

```powershell
pnpm pack:module <id>
pnpm bundle:modules
```

[pack 스크립트](../tools/scripts/pack-module.ts)는 모듈을 Vite로 빌드한 뒤 매니페스트·아이콘과 묶어 `target/deckmod/<id>-<version>.deckmod`를 만들어요. [bundle 스크립트](../tools/scripts/bundle-modules.ts)는 모든 모듈을 묶어 호스트의 `resources/modules` 아래 패키지와 `index.json`을 생성해요. `pnpm tauri dev`와 `pnpm tauri build`의 프론트엔드 단계도 기본 모듈 번들을 먼저 생성하므로, 이미 실행 중인 앱에서 소스만 고친 경우에는 다시 실행해 확인해요([데스크톱 스크립트](../apps/desktop/package.json)).

패키지에는 [카탈로그·패키지 규격](spec/catalog.md#2-패키지-deckmod)의 크기·경로·해시 검증이 적용돼요. 압축 패키지 20MB, 해제 합계 50MB 제한 안에 에셋·WASM·라이브러리가 들어가는지 확인해요. `pack` 성공은 사용자 화면의 검증이나 설치본 검증을 대신하지 않아요. 앱 설치본까지 작업 범위에 들어가면 `pnpm tauri build` 후 해당 설치본에서도 도구를 열어 확인해요.

사용자에게 보이는 변경은 [모듈 버전 규칙](spec/versioning.md#2-모듈-semver)에 맞게 `module.json` 버전과 모듈 `CHANGELOG.md`에 기록해요. 최종 변경 범위와 검증 결과를 리뷰할 수 있게 정리하고, 커밋할 때는 Conventional Commits와 `git commit -s`를 사용해요(GEN-009). 원래 코드·에셋의 저자 표기와 라이선스는 유지해요(GEN-007, MOD-012).

## 5. 구현 전에 제안으로 분리할 사항

아래 요구가 실제 이식 범위에 나타나면 해당 구현을 시작하기 전에 [정지 조건과 제안서](spec/process.md#2-정지-조건과-제안서)를 적용해요. 지금은 해당 변경을 구현하거나 승인받으려는 작업이 없어요.

- 새 캡 도입이나 기존 캡의 major 변경.
- 매니페스트·브리지·카탈로그 포맷, CSP·Tauri ACL·updater·커스텀 프로토콜 변경.
- `crates/*`, `apps/desktop`, `packages/*`의 런타임 의존성 추가. 모듈 의존성도 라이선스 검사를 통과해야 해요.
- 라이선스·저작자 표기 파일 변경, 사용자 파일 삭제·덮어쓰기 동작 도입, 규칙 충돌.

예정된 `fs` 읽기·저장 확장도 API와 전송 방식이 아직 확정되지 않았으므로 [예정 캡 설명](spec/capabilities.md#5-예정-캡)에 따라 제안서와 ADR이 먼저 필요해요. 메서드 추가는 CAP-004의 minor 변경 규칙을 따르며, 새 캡·major 변경과 동일한 것으로 분류하지 않아요. 다만 저장·덮어쓰기와 전송 방식에 따라 다른 정지 조건이 함께 적용될 수 있어요.

제안서에는 필요한 기능, 기존 캡 조합·JS/WASM 대안, API와 버전 영향, 개인정보·보안 영향, 필요한 승인을 담아요. 승인 대상 영역을 임의로 구현하지 않고, 그 영역에 의존하지 않는 순수 계산 분리와 테스트 준비는 계속할 수 있어요. 현재 받은 소스와 사용자 답변을 바탕으로 [제품 개발 계획 초안](PRODUCT_PLAN.md)의 각 작업을 이 절차에 연결해요.
